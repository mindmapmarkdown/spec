# 워크드 예제 읽는 법

사양의 예제는 **입력 문서**와 **그것이 만들어내야 하는 트리**를 함께 적고, 트리는
JSON으로 쓴다. 이 문서는 JSON을 다뤄본 적 없는 사람을 위해 그것을 읽는 법을
설명한다.

> **번역본이다.** 정본은 영문 [`docs/reading-examples.md`](../reading-examples.md)이며,
> 이 번역과 원문이 어긋나면 **원문이 이긴다**. 어긋난 곳을 발견하면 그것은 이 파일의
> 결함이므로 [이슈로 알려달라](https://github.com/mindmapmarkdown/spec/issues).

**이 문서는 참고용(informative)이며 아무것도 정의하지 않는다.**

> **여기서 설명하는 것 중 일부는 확정이 아니라 제안이다.** 노드의 *종류(kind)*와
> 트리의 JSON 인코딩은 [코멘트 기간이 열려 있는 RFC](https://github.com/mindmapmarkdown/spec/pull/4)에서
> 온 것이며, 바뀌거나 기각될 수 있다. JSON 문법 자체와 예제 블록의 모양은 논쟁
> 대상이 아니다.

## 기호 다섯 개로 보는 JSON

JSON은 **구조가 있는 데이터를 글자로 적는 방법**이다. 프로그램끼리 데이터를 주고받기
위해 만들어졌다. 여기서 필요한 문법은 기호 다섯 개가 전부다.

| | | |
|---|---|---|
| `{ }` | **객체** | 이름이 붙은 값들의 묶음 |
| `[ ]` | **배열** | 순서가 있는 값의 목록 |
| `" "` | **문자열** | 글자 값 |
| `:` | | 이름과 값을 잇는다 |
| `,` | | 항목과 항목을 구분한다 |

**객체**는 담고 있는 것에 이름을 붙인다.

```json
{ "이름": "홍길동", "출생": 1815 }
```

각 항목에 이름이 있으므로 **순서는 중요하지 않다.**

**배열**은 순서만 갖는다.

```json
[ "사과", "배", "자두" ]
```

이름이 없다. 첫째가 사과, 둘째가 배다. 순서를 바꾸면 다른 뜻이 된다.

**이 둘은 서로 안에 겹쳐 넣을 수 있고, 그 겹침이 곧 계층이다.**

```json
{
  "이름": "홍길동",
  "자녀": [
    { "이름": "홍철수" },
    { "이름": "홍영희" }
  ]
}
```

사람이 하나 있고, 그 `자녀` 항목에 **목록**이 들어 있고, 목록의 각 원소가 또 사람
객체다. JSON에서 트리란 이것이 전부이며, 사양의 예제도 정확히 이 모양이다.

하나 더 알아둘 것:

```json
"자녀": []
```

**빈 배열**이다. 항목은 있는데 안에 아무것도 없다는 뜻이다.

## 예제 블록의 모양

예제는 정보 문자열이 `example`인 울타리 블록이다.

````markdown
```example
# Project
## Install
.
{"children":[ … ]}
```
````

`.`만 있는 줄이 두 부분을 나눈다. **위가 들어가는 마크다운, 아래가 나와야 하는
트리**다.

구현자는 위쪽을 자기 리더에 통과시키고 결과를 아래쪽과 비교한다. 모든 예제에서
일치하는 것이 적합하다는 뜻이다. 예제는 `tools/extract-examples.mjs`가
`examples/examples.json`으로 기계적으로 추출하며, 그 파일은 생성물이고 손으로 고치지
않는다.

사양 안의 예제는 자리를 아끼려고 빽빽하게 쓰여 있다. 아래의 JSON은 모두 줄을 벌려
적었다. **내용은 완전히 같다** — JSON에서 토큰 사이의 공백은 아무 의미도 갖지 않는다.

## 예제 1 뜯어보기

입력:

```markdown
# Project
## Install
```

기대 트리:

```json
{
  "children": [
    {
      "kind": "section",
      "label": "Project",
      "content": [],
      "children": [
        {
          "kind": "section",
          "label": "Install",
          "content": [],
          "children": []
        }
      ]
    }
  ]
}
```

**맨 바깥 객체가 루트다.** 항목이 `children` 하나뿐이고 자기 이름이 없다 — `label`도
`kind`도 없다. **루트에 대응하는 글자가 문서에 없기 때문이다.** `# Project`는 루트가
아니라 **루트의 첫 자식**이다. 루트는 전체를 담는 보이지 않는 상자다.

**그 안의 노드는 항목이 정확히 네 개다.**

| | |
|---|---|
| `kind` | 헤딩으로 쓰였는지, 리스트 항목으로 쓰였는지 |
| `label` | 노드의 보이는 글자 |
| `content` | 노드에 붙은 블록 자료 — 문단·표·코드 |
| `children` | 그 아래의 노드들 |

그러니 `Project`는 헤딩으로 쓰인 노드이고, 이름표는 `Project`이며, 붙은 것은 없고,
자식이 하나 있다. `Install`도 같고, `children`이 비어 있으니 그 가지는 거기서 끝난다.

```
마크다운                  트리
────────────────────────────────────────────
                      (루트)     자기 글자가 없다
# Project        →      └─ Project       kind: section
## Install       →          └─ Install     kind: section
```

## 예제 2와 단 하나의 차이

입력:

```markdown
- Project
  - Install
```

기대 트리:

```json
{
  "children": [
    {
      "kind": "item",
      "label": "Project",
      "content": [],
      "children": [
        {
          "kind": "item",
          "label": "Install",
          "content": [],
          "children": []
        }
      ]
    }
  ]
}
```

예제 1과 비교해보라. 이름표도, 중첩도, 나머지 전부가 같다 — **`kind`가 `section`이
아니라 `item`이라는 것만 다르다.**

그리고 사양은 그 둘을 **서로 다른 트리**라고 부른다. **그 한 단어가 열려 있는 RFC
제안의 전부다.**

## kind가 뜻하는 것

| 값 | 마크다운 표기 | 주장하는 것 |
|---|---|---|
| `section` | 헤딩 — `#`, `##`, `###` … | *여기서부터 문서의 한 구획이 시작된다* |
| `item` | 리스트 항목 — `-` | *이것은 나열 중 하나다* |

이 구분을 정규화해서 없애지 않고 트리에 남기는 이유는, **읽는 사람이 그 둘을 같은
것으로 경험하지 않기 때문**이다. `## 설치`는 절의 시작을 알리고, `- 설치`는 나열된
것 중 하나다. 그것을 보존하는 것은 **문서가 말하는 바를 보존하는 것**이지 어떻게
보이는지를 보존하는 것이 아니다. 색깔·위치·접힘 상태야말로 보이는 것이고, 그것들은
사이드카에 속한다([`overview.md`](overview.md)가 그 구분을 설명한다).

이것이 실제로 사주는 것 — 문서가 도구로 나갔다 돌아올 때:

```markdown
# 설치                            # 설치
                         →
## 요구사항                       ## 요구사항
```

`kind`가 트리에 없으면, 같은 왕복이 이렇게 돌려줘도 된다.

```markdown
- 설치
  - 요구사항
```

계층은 살아남았고 문서는 죽었다. **`kind`를 유지하는 것이 위쪽 결과를 희망이 아니라
요구사항으로 만든다.**

## 빈 배열을 굳이 적는 이유

처음 보면 군더더기처럼 보이는 부분이다.

```json
"content": [],
"children": []
```

비어 있으면 그냥 빼면 안 되나? **안 된다. 그러면 같은 트리를 두 가지로 적을 수 있게
되기 때문이다.**

```json
{"kind":"item","label":"npm","content":[],"children":[]}
{"kind":"item","label":"npm"}
```

서로 다른 두 글자, 같은 뜻. 테스트 스위트는 **"이 두 트리가 같은가"**에 답하려고
존재하는데, 표기 방법을 여러 개 허용하는 인코딩은 그 질문에 답하기 어렵게 만든다 —
모호성을 없애는 것이 존재 이유의 전부인 그 표기법 안에서.

그래서 모든 항목을 항상 적는다. 장황해지는 것은 사실이고, **그 비용은 그것을 쓰는
사람이 아니라 자동 생성되는 파일이 치른다.**

## 구속력 있는 규칙은 어디에 있나

위의 어떤 것도 규칙이 아니다. 규칙은 이렇다.

- **예제 블록 형식** — `tools/extract-examples.mjs`와
  [`CONTRIBUTING.md` §6](../../CONTRIBUTING.md#6-working-on-the-specification-text).
- **트리 인코딩과 `kind`** — [열려 있는 RFC](https://github.com/mindmapmarkdown/spec/pull/4)의
  §2.1과 §2.6. 승인되기 전까지 이것들은 제안이다.
- **적합성** — [`spec.md` §1.2](../../spec.md#12-conformance).

예제와 이 문서가 어긋나면 **예제가 옳다.**
