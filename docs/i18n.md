# How this project handles languages

**Translations** — [한국어](ko/i18n.md)

Which text counts when two languages disagree, how a translation gets written,
and what this project will not do to produce one.

**This document is informative. It defines nothing.** The requirements it
mentions are stated normatively in [`spec.md`](../spec.md), and where the two
disagree, `spec.md` wins. This English text is the authoritative version of this
file.

It covers this repository — `spec.md`, `docs/**` and `rfcs/**`, which already
carry Korean translations — and
[`mindmapmarkdown/website`](https://github.com/mindmapmarkdown/website), which
serves [mindmapmarkdown.org](https://www.mindmapmarkdown.org) in English,
Korean, Japanese and Simplified Chinese from `src/i18n/content.js` with English
as its source.

---

## What is authoritative

The English `spec.md` is the specification. **A translation of a requirement is
not a requirement:** an implementation is conforming or not against the English
text, and a reader who finds a disagreement has found a defect in the
translation.

Four things are never translated, in any document, informative ones included:

- the BCP 14 keywords — MUST, MUST NOT, SHOULD, SHOULD NOT, MAY, and the rest
  of §1.3's list;
- rule identifiers — `L-14`, `P-8`, `E-5`, `S-7` and the others;
- the contents of fenced `example` blocks, which are normative and are
  extracted mechanically into [the conformance
  suite](../examples/examples.json);
- member names of the tree encoding — `label`, `source`, `content`, `children`,
  `kind`, `block`.

A page that cannot keep these fixed is not published in that language.

## How a translation is written

By hand, by a person, in a commit they sign off under the DCO
([`CONTRIBUTING.md` §5](../CONTRIBUTING.md#5-dco-sign-off)). Translations live
beside the English files — [`docs/ko/overview.md`](ko/overview.md) next to
[`docs/overview.md`](overview.md) — and carry the licence of the text they
translate, CC-BY-4.0 for prose ([`LICENSE`](../LICENSE)).

Every translated page opens with a notice saying that it is a translation, that
the English is authoritative, that it may lag behind, and where to report a
mismatch. **A translation that has fallen behind is a defect of the translated
file; the English file is not held back for it.** Relative links are used
throughout so that a fork or a translation keeps working
([`CONTRIBUTING.md` §6](../CONTRIBUTING.md#6-working-on-the-specification-text)),
and `tools/check-links.mjs` checks them on every pull request.

## Machine translation

Machine translation is allowed only when all five of these hold:

1. **It runs when the site is built, not when a reader opens it.** No request
   leaves a reader's browser for anyone but the site they chose to visit.
2. **A person reviews the output before it is published.**
3. **The page says it is machine translated**, in the same notice every
   translation carries.
4. **It never runs over normative material.** The four excluded items above are
   kept out of what is sent structurally — by the shape of the input, not by a
   list of words a translator is asked to spare.
5. **The output is committed like any other file**, so that it can be read in a
   diff and reverted.

**Runtime translation widgets are not used**, however convenient. A reader
should be able to read a page of this project without being announced to a
third party.

## Record: translate.js, evaluated and declined on 2026-11-10

The author of [translate.js](https://github.com/xnx3/translate) wrote to the
maintainer on 2026-10-23, offering it for this project's documents. The reply
the same day set out the boundaries above and asked five questions, and a
detailed answer arrived on 2026-11-07. That answer was candid: it declined to
assert a retention policy, a vendor agreement, a quota figure or a completed
telemetry audit that its author could not verify from the source. **That candour
is why a decision could be reached rather than deferred.**

It was declined, for four reasons, in the order they weighed:

- **Reader disclosure.** At the revision reviewed, `df9d77c`, the non-edge path
  sends `window.location.href` as a `currentpage` header, so a reader of a
  translated page would have the page they are reading sent to a third-party
  server. Its author confirmed there is no supported switch to disable this. A
  patched local copy would fix it, at the price of maintaining a patched fork of
  a translation client.
- **No statement to quote.** The hosted service has no retention or
  training-use statement, and the `client.edge` path depends on an endpoint
  neither party controls.
- **No planable quota.** The published daily limits could not be resolved into
  a figure a site could be planned around.
- **No guarantee for keywords.** Its author was explicit that the glossary
  feature is not a guarantee that a given token survives. On a standards page a
  MUST that quietly becomes a SHOULD is the one failure that cannot be
  accepted — including on a page labelled as machine translated, because a
  reader who copies a keyword out of it is no less misled.

**None of this is a judgement on the quality of the software.** It is a
statement that a runtime translation client does not fit a project whose text is
its product.

## What would change the answer

Demand for a language the maintainer cannot cover by hand. If that arrives, the
first thing to evaluate is a private deployment — the backend, the model and the
endpoint under this project's control — which is what translate.js's own author
recommended where the uncertainties of a public service are unacceptable. Any
adoption would still have to satisfy the five conditions above, and would start
as a reversible trial on one informative page.

If this project ever vendors a third-party script, it pins the exact revision,
records its hash, and preserves the licence notice of the artifact it adopted.
